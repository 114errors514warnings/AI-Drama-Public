## TODO-1 输入框自动换行

- **状态**：待做
- **现象**：消息输入框是单行 `<input>`，长文本无法换行编辑，回车直接发送。
- **定位**：`frontend/index.html` 的 `#msg-input` 为 `<input>`；`frontend/app.js::bindEvents` 绑定 `keydown` 的 Enter 直接 `sendMessage()`。
- **建议方向**：
  - 改为自适应高度的 `<textarea>`（随内容增高，设最大高度后内部滚动）；
  - `Enter` 发送、`Shift+Enter` 换行（保持现有习惯）；
  - 输入框固定在底部，消息区独立滚动（现有布局不受影响）。
- **验收**：粘贴多行文本可正常显示与编辑；`Shift+Enter` 换行、`Enter` 发送；输入框高度随内容增长、超限后滚动。

## TODO-2 输入框新增「对话轮次」选项 + 需求细化机制

- **状态**：待做（需求需先确认，见下）
- **现象/需求**：
  1. 输入框区域额外增加一个**选项栏，允许选择"对话轮次"**（如 1 / 3 / 5 轮 / 自定义）。
  2. 需要额外机制：**对话轮次较多时，要"细化用户的需求"**——即在指定的多轮里，让用户需求的发展**更加详细地展开推进**，而不是**续写/复述用户的需求**。
     （即：把用户一句需求拆成一条可推进的多轮剧情线，逐轮深化；禁止每轮都改写同一句话。）
- **需确认点**：
  - 「对话轮次」是"连续自动推进 N 轮群聊"，还是"把一句需求拆成 N 轮的规划"？
  - 轮次是每轮都等用户确认，还是自动连跑 N 轮？
  - 是否与现有导演规划 JSON 的 `event`/`narration` 对齐（把细化结果写进规划而非转录）？
- **建议方向**：
  - 导演提示词增加"多轮大纲"输出：一次性产出 N 轮的推进要点（每轮一个递进目标），存为会话的 `plans`（场外，不污染转录）；
  - 每轮只从大纲取"本轮的推进点"，避免复述用户原话；
  - 前端轮次选择写入 `config`/会话；后端 `run_group_turn` 支持按大纲推进。
- **验收**：选 3 轮后，三轮的剧情/事件呈递进关系且无重复复述；第 N 轮结束后剧情明显比单轮更完整。

## TODO-3 「清空对话」未清除与单个 Agent 的对话

- **状态**：待做（已定位）
- **现象**：清空对话后，与单个 Agent（如导演）的**场外对话记录仍然保留**，切到单 Agent 视图仍能看到旧对话。
- **定位**：`backend/session.py::WorldSession.clear_transcript()` 只重置 `transcript / world`，**没有清 `side_chats`**；
  `backend/main.py` 的 `POST /api/sessions/{sid}/clear` → `ws.clear_transcript()`。
  前端单 Agent 视图走 `GET /api/sessions/{sid}/side_chat/{agent}`，读的正是 `side_chats`。
- **影响范围**：**所有 Agent**，非导演专属（当前仅在导演上测出，其他 Agent 未逐一验证，机制上必然相同）。
- **建议方向**：
  - `clear_transcript()` 内一并清空 `self.side_chats = {}`（或在 UI 上提供独立开关"是否同时清除场外对话"）；
  - 若"清空对话保留记忆"是既定语义，需明确"记忆保留、场外对话清除"。
- **验收**：清空对话后，群聊转录与所有 Agent 的单聊记录均为空；角色长期记忆仍保留。

## TODO-4 导演回复意义不明 / 未继承此前讨论的剧情结构

- **状态**：复现中（用户反馈"暂时无法测试"）
- **可测试接口（已提供）**：见《API接口参考.md》§十一「调试 / 自检接口」——
  `GET /debug/group/preview`、`POST /debug/group/plan`、
  `GET /debug/agent/messages`、`POST /debug/agent/turn`（默认 dry-run）、
  `GET /debug/context`、`DELETE /debug/side-chats`。
  其中 `debug/agent/messages` 的 `system_prompt_requires_json=true` 即现象 1 的直接证据；
  `debug/context` 的 `side_chats_used_in_group_plan=false` 即现象 2 的直接证据。
- **现象**：
  1. 与**导演**对话时，回复是一段**规划 JSON 原文**（`{ "narration": ..., "participants": ..., "location": ..., "date": ..., "time_of_day": ..., "event": ... }`），
     而不是人话/旁白 → 观感"意义不明"。
  2. 之前与导演讨论过剧情结构（如"场景出场角色白名单""缺陷归纳"等），但后续**没有继承**之前讨论的剧情结构。
- **初步定位（未完全复现）**：
  - 现象 1：`backend/director.py::run_agent_turn()` 单聊时直接使用 `agent.system_prompt`，
    而导演的 System Prompt（`prompts.build_director_system_prompt`）要求"**始终只输出严格 JSON**"，
    因此与导演单聊天然会得到 JSON。→ 需要一个"单聊模式"的导演提示词（说话/确认，而非输出 JSON）。
  - 现象 2：`side_chats`（场外单聊）与群聊编排**完全隔离**——`_director_plan()` 用的是
    `transcript` 历史 + 导演长期记忆 `long_memory`，**不读取 `side_chats`**。
    这是 V2"场外不污染"的刻意设计，但与"单聊讨论要带入群聊规划"的期望冲突。
    → 需要一座"导演单聊 → 沉淀为调度备忘（`long_memory`/plans）→ 群聊规划引用"的桥。
- **建议方向**：
  - 单聊模式按 role 切换提示词：导演/功能 Agent 单聊用"对话版"提示词（不强制 JSON）；
  - 单聊结束时把"确认的剧情结构/白名单"沉淀为导演的调度备忘（经用户确认），群聊编排显式引用；
  - 明确"单聊"和"群聊"的边界，避免场外内容直接污染转录。
- **验收**：与导演单聊得到自然语言回复；单聊确认的结构能在下一轮群聊规划中被引用（可观测/可验证）。

## TODO-5 各 Agent 单聊记忆 → 群聊生成需据此调整

- **状态**：待做（需先确认"记忆"口径）
- **需求**：与各 Agent 对话后会**留存记忆**；在**群聊模式**下，这些 Agent 生成的内容需要**基于这些记忆进行调整**
  （即单聊里形成的结论/偏好/剧情结构，应当影响该 Agent 在群聊中的产出）。
- **现状定位（代码事实）**：
  - 单聊 `director.run_agent_turn()` 只把对话写入 `session.side_chats[agent]` 并落盘，
    **不抽取长期记忆**（`extract_memories()` 仅在群聊整轮 `_run_group_turn()` 里调用，单聊不调用 `long_memory`）。
  - 群聊 `_reply_as()` 只用 `agent.system_prompt`（内含 `long_memory`）+ 群聊转录，**不读取 `side_chats`**。
  - 结论：当前"单聊 → 群聊"**没有任何信息通路**（与 TODO-4 现象 2 同源，但本项覆盖**所有 Agent**，且聚焦"记忆"而非仅导演的剧情结构）。
- **待确认**：
  - "留存记忆"指 A）侧栏单聊历史（`side_chats`）就算记忆，还是 B）要把单聊结论**沉淀进该 Agent 的长期记忆**（`long_memory`，走既有去重/冲突消解治理）？
  - 调整方式：自动把记忆注入提示词，还是提供"是否采纳"的确认开关？
  - 隔离边界：导演/世界的"调度类记忆"是否允许影响角色产出（避免把场外调度灌进角色）。
- **建议方向**：
  - 单聊结束时按 Agent 类型抽取"该 Agent 需要长期记住"的结论（角色=人设/经历/关系；导演=调度偏好/剧情结构；世界=规则澄清；梗概=主线要点），
    经 `memory_ops.merge_facts` 治理后写入其 `long_memory`；
  - 群聊生成时，除 `system_prompt` 外按当前场景检索该 Agent 的 `long_memory` 注入（已有 `memory_usage_rate` 可观测）；
  - 明确边界：调度类记忆只进对应 Agent 提示词，不写入群聊转录、不灌给角色。
- **验收**：与某 Agent 单聊确认一条信息 → 下一轮群聊中该 Agent 的产出体现该信息（可经 `debug/context` 与 `/metrics` 的 `memory_usage_rate` 验证）。
